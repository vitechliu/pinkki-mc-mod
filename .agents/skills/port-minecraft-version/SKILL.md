# 按需适配 Minecraft 版本

在本仓库工作，从仓库根目录执行以下命令。先读取 [AGENTS.md](../../../AGENTS.md) 和 [开发流程](../../../docs/development-workflow.md)。日常主目标为 1.20.1 Forge；本 skill 只处理用户要求的其他版本。

## 明确本次范围

- 用户指定 1.21.1 时只适配 1.21.1 NeoForge，指定 1.19.1 时只适配 1.19.1 Forge，不自动顺带处理另一个目标。
- 用户只说“其他版本”且范围不明时，询问要哪些目标，同时先整理待适配清单，不默认跑全部版本。
- 默认补齐指定目标的全部积压功能。用户限定部分功能时只做该部分，保留其余待办，不推进完整检查点。
- 新增目标先明确 Minecraft 精确版本、加载器及 JDK；从官方资料核对工具链，再创建独立适配目录。不要推测相邻 Minecraft 版本或不同加载器通用。
- 沿用默认禁止实机测试规则，仅执行适用的无头验证。此 skill 不自动授权发布、推送标签、启动客户端、修改真实游戏实例或部署生产服务。

## 建立待补清单

1. 运行 `python3 scripts/targets.py status`，读取 [检查点](../../../docs/porting/status.json) 中指定目标的源码参照与证据范围。
2. 阅读 [功能变更记录](../../../docs/changes/)，找到该目标未完成的功能、修复、移除和契约变化；将其中验收场景转成适配清单。
3. 对比上次 `source_ref` 到当前 HEAD 的 Git 差异，并检查工作区、暂存区和未跟踪源码。重点检查 `common/src/main/`、`versions/1.20.1/`、共同元数据及共享构建脚本，不只看文件名或变更标题。
4. 源码为事实依据，日志提供需求与验收语义；漏写日志时补记录。指纹不匹配仅表示需要审查/验证，不能自动推断必须复制整份源码。
5. 初始检查点只证明空 mod 骨架的历史构建及无头服务端，不包含第三方 mod、真实多人或次要版本 GUI 的兼容性证明。

清单覆盖用户可见行为、注册 ID、配置、网络协议、持久化、资源格式、事件阶段和客户端/服务端边界；按实际需求列出，不添加尚无需求的玩法。

## 实施适配

- 共享业务尽量留在 Java 17 的纯 Java 核心；Minecraft 与加载器 API 差异放指定版本的适配层，不依赖运行时版本判断或大量反射。
- 保留用户当前主版本语义，移植功能移除和修复时也清理目标的旧行为，不只复制新增项。
- 资源格式、注册/事件 API、网络和保存格式按目标实际要求处理，不机械复用主版本 JSON。
- 若修正共享代码，针对 1.20.1 做必要回归；不要因此扩展到其他未指定版本。
- 对有意不支持的内容，记录“不适用”的具体理由；存在产品语义取舍时向用户确认，不悄悄删功能。

新增目标时，检查 `config/minecraft-targets.json`、版本目录及 Wrapper、`scripts/mod.sh` 的 JDK 选择、`scripts/verify-artifact.py` 的加载器/Java 目标、`scripts/hmcl-test.py` 与 `scripts/smoke-server.py` 支持范围、`scripts/build-all.sh` 及相关文档。以实际调用关系判断更新范围，不只加一个 CI 矩阵项。新增源码根目录时也同步 `scripts/targets.py` 的源码指纹范围。

## 验证与收尾

对指定目标执行构建、发行 JAR 校验和适用的无头行为验证，例如：

```bash
./scripts/mod.sh 1.21.1 build
python3 scripts/verify-artifact.py 1.21.1
python3 scripts/smoke-server.py 1.21.1
```

冒烟只证明加载和世界启动，不能替代实际功能测试。按变更补充有意义的单元测试、无头 GameTest 或服务端场景；没有 GameTest 时不运行空测试套件。只能通过 GUI 验收的行为标注待人工验证，并给用户操作步骤。

更新每份功能记录的指定目标状态、实际命令、日志/证据和未验证范围。全部积压功能均已适配、验证结果足以支持声明后，才执行：

```bash
python3 scripts/targets.py checkpoint --targets 1.21.1 \
  --evidence .local/porting-1.21.1-verification.log
python3 scripts/targets.py status --targets 1.21.1 --check
```

证据文件必须真实存在，并说明完成的功能场景和证明边界；不能创建空泛的“成功”文本来推进检查点。部分适配或失败时保留旧检查点，记录剩余事项。先完成必要源码/元数据修改再记录指纹；之后再次修改相关文件需要重新验证和记录。

最后报告适配目标、补齐内容、实际验证、未完成项目及是否推进检查点。源码、变更记录和检查点应在同一提交中交付；提交或推送遵循用户本次授权。部署和发布仅在用户另外要求时执行，参考 [发布流程](../../../docs/release.md)。
